# Redis / MQ / 进程宕机与重复消息验收

日期：2026-10-20。目标是验证真实依赖故障、进程退出和重复投递下，订单能够恢复，且不会在同一轮重复接单或重复入账。

## 环境与注入方式

使用 `scripts/verify-fault-recovery.py` 为每轮创建独立 MySQL schema、Redis、RocketMQ Broker/NameServer 与网络，只对带本轮归属标签的容器执行停止、重启、删除。业务操作经真实 HTTP；SQL 只用于初始化测试账户、登记 run、读取事实以及持有/释放测试订单行锁，不修改业务状态或截止时间来伪造恢复。

- API 与 worker 分别为独立 Java 进程，用 SIGKILL 制造宕机，再从同一数据库重启。
- Redis 禁用持久化，真实 kill/start 后内存键丢失。保留默认跑腿限流；Redis 超时显式为 1000 毫秒，以限制故障验收中的阻塞时间。
- Broker 真实 kill/start；始终保持 `dash.mq.enabled=true`，不以 Noop 消息适配器代替依赖故障。
- 确认超时 30 秒，自动结算 45 秒，数据库兜底扫描 5 秒；Broker 事务回查周期 5 秒。时间参数用于本机故障验证，不作为生产 SLA。
- `scripts/publish-fault-messages.py` 使用现有 RocketMQ 5 SDK 向本轮 Broker 实际重复发送相同业务键和消息体，保留每条发送/事务提交回执；再检查消费者日志与数据库副作用。
- MySQL TCP 代理在指定结算事务收到真实 COMMIT OK 后丢弃该响应并断开连接，证明“数据库已经提交但应用不知道”的恢复路径。HTTP 代理另制造“API 已成功但客户端未收到响应”的场景。

从后端目录运行：

```bash
# Java 业务代码修改后必须先全量 install，再运行已更新的 JAR。
python3 scripts/verify-fault-recovery.py
```

前提与上一轮一致：本机 `dash-mysql` 可用，Docker 镜像已具备，Java/Python 可执行。报告、数据库及故障日志保留；本轮进程和容器在结束时回收，清理失败会使整体验收失败。

## 发现与修复

### 自动结算消息没有校验到期时间

旧实现的 `AutoSettleConsumer` 直接调用资金结算，只要订单已送达，提前消息就会结算。旧 JAR 的真实基线运行 `20261020-215443-d8ae` 中，订单 21:56:28.513 送达，21:56:34.197 已结算，比 45 秒窗口提前 **39316 毫秒**。三个实际 MQ 消费成功结果为 1 SETTLED、2 CONFLICT，证明单次入账幂等不能替代时间约束。

新增 `AutoSettleErrandUseCase`，MQ 与扫描统一根据主库 `NOW(3)`、DELIVERED 状态及版本校验到期。提前或过时消息跳过，到期后仍复用原资金事务及唯一索引。发单人手动确认结算仍允许在自动窗口内进行。

### 本地资金事务结果未知时错误回滚半消息

原 `RocketMqFundEventAdapter` 将 committed 初始化为 false；本地 COMMIT 已成功但 ACK 丢失时，异常会让 finally 回滚 MQ 半消息，导致已有资金流水的通知永久丢失。

修复为：本地工作明确返回 true/false 才分别提交/回滚半消息；异常保持半消息未决并原样抛出，由 Broker 回查主库流水裁决。主库不可读时返回 UNKNOWN，不能当成“流水不存在”。

### Redis 鉴权故障返回通用 500

真实基线中，Redis kill 后 Session 鉴权返回 HTTP 500 / INTERNAL_ERROR，没有 Retry-After。订单仍为 PUBLISHED，未错误放行，但客户端无法识别依赖退避。

鉴权拦截器现在仅转换连接失败、查询超时这两类依赖异常，返回 HTTP 503 / DEPENDENCY_UNAVAILABLE 和 Retry-After: 1，且不进入业务控制器。无效或丢失 Session 继续返回 401；不会为了查询恢复而绕过身份校验。Redis 内存丢失后需重新登录，再用原 UUID 查询持久结果。

基线证据：[真实缺陷记录](../verification/fault-recovery/20261020-215443-d8ae/baseline-findings.json)、[原始运行报告](../verification/fault-recovery/20261020-215443-d8ae/run-report.json)。该基线轮有一处只读报告 SQL 误用了不存在的 settled_at 列，已改为读取状态日志；时间证据由保留数据库只读补取，原始失败报告未改写。

### Redis 清空后不完整 Bloom 隐藏旧订单

发布事务提交与 Bloom 登记不具备原子性；Redis 清空后，先发布的新单还会建立只包含新 ID 的 Bloom。原详情查询把 Bloom 阴性当成不存在，导致数据库里正常的旧订单返回 ERRAND_NOT_FOUND，页面无法继续操作。

修改详情缓存未命中路径：Bloom 只作提示，存在性回源数据库确认；不存在的 ID 仍写短期空值缓存。新增两项真实 Redis/DB 回归，覆盖不完整 Bloom 和发布提交后登记失败。真实故障脚本另覆盖“清空 Redis → 登录 → 发布新单 → 查询旧单详情与我的任务 → 原订单继续完成”。参见 [缓存布隆故障恢复说明](缓存布隆故障恢复说明.md)。

### 验收注入器的协议修正

首次修复后完整运行 `20261020-215944-01c8` 在 COMMIT ACK 用例失败：业务正常提交，但代理未触发截断，该轮不能视为完整故障通过。定位到 Connector/J 的 Query Attributes 协议字段位于 COM_QUERY 的 SQL 前，旧代理没有识别带协议头的 COMMIT。代理已根据握手协商解析协议，仅针对指定业务流水所在事务截断成功回执；原失败报告保留，不改写为成功。
