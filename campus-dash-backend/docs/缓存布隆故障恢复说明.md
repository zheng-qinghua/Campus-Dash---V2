# 缓存布隆故障恢复说明

详情查询以数据库记录为任务存在性的权威。Bloom 登记仅供显式诊断与重建，详情读路径不再同步查询 Bloom。缓存未命中时回源数据库，数据库确认不存在后才写入短期空值缓存；HTTP 详情还会通过实时主键查询核对存在性和动作集合。

Redis 清空后，Bloom 完全缺失时原实现会保守放行，但第一笔新发布会创建只含新订单的不完整过滤器。旧订单随后被误判为不存在，而启动时执行一次的重建任务无法在运行期间自动修复。发布数据库事务提交后、Bloom 登记之前的进程退出或 Redis 写失败，也会留下同样的遗漏。

布隆算法对已成功登记的数据不产生假阴性，不等于整个业务登记链路不会漏项。当前没有覆盖全部数据库记录的完备性协议，因此不能用布隆阴性代替数据库查询。重建仍可补充登记信息，但详情正确性不依赖重建是否完成。

本次修复保留详情缓存、短期空值缓存和逻辑过期重建。单独调用缓存用例时，同一不存在 ID 在空缓存有效期内不会再次回源。**HTTP 详情接口仍必须实时查询数据库**：发布提交前的负缓存、或发布后迟到的负缓存都不能否决存在性。因此缓存命中统计不等于 HTTP 接口的数据库请求次数；负缓存命中的 HTTP 请求会做一次主键查询，冷负缓存请求会做两次。不同随机 ID 的持续请求不再承诺由 Bloom 实现零回源。

回归覆盖：

- 真实 Redis 中删除测试专用 Bloom，再只登记新订单，旧订单详情仍可从数据库恢复并缓存。
- 真实发布事务提交后注入登记异常，订单详情仍可读取，不能写成空缓存。
- 一千个不存在的 ID 各首次回源一次，重复查询全部命中短期空值缓存。

真实 HTTP 故障验收应在 Redis 清空恢复后先发布新订单，再读取清空前的旧订单详情，同时与“我的发布”列表及数据库状态、轮次对照。只轮询数据库或幂等结果接口，无法发现详情不可见的问题。

2026-10-20 后续复核补充：用真实 HTTP/MySQL/Redis 和闩锁分别固定“先负缓存后提交”与“先提交后迟到负缓存”的时序，验证订单仍可见、角色及动作正确，真实不存在的订单仍返回 ERRAND_NOT_FOUND。详情缓存用例也验证不会再调用可能阻塞的 Bloom 观察接口。完整结果见 [四项修复复核记录](四项故障修复复核记录.md)。
